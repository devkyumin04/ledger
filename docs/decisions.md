## 아키텍처

### ADR-001. 화면은 정적 파일, 데이터는 `/api` JSON + Vanilla JS

- **문제** — 화면과 API를 어떻게 나눌 것인가
- **대안** — 서버 템플릿(Thymeleaf) / React·Vue SPA / Vanilla JS + REST
- **선택** — Vanilla JS 정적 파일 + `/api` JSON. **Spring Boot 한 프로세스가 둘 다 서빙**(별도 프론트 서버·빌드 도구 없음). PWA 전환 예정
- **표현 정리 (2026-09-18)** — 원래 "REST API 완전 분리"라고 적었는데 서버를 나눈다는 뜻으로 읽혀 고침. 나뉜 건 프로세스가 아니라 **책임**(화면 vs 데이터)이고, 이게 PWA·소셜 로그인 후 자체 JWT 발급의 전제. Thymeleaf 로 되돌리는 게 오히려 화면 8개를 다시 쓰는 일
- **감수** — 프레임워크 없이 DOM을 직접 다뤄야 함. 화면 규모가 커지면 관리 비용 증가

### ADR-002. EC2 한 대에 전부 올림 (RDS 미사용)

- **문제** — 월 예산 5~6만원 안에서 24시간 운영
- **대안** — RDS + EC2 / EC2 단일 / 서버리스
- **선택** — t3.medium 한 대에 Spring Boot + MySQL + 임베딩 모델 + Redis(컨테이너) 전부 구동. 스왑 대신 여유 메모리 확보
- **감수** — 단일 장애점. DB 백업·복구를 직접 관리해야 함
- **배경** — AWS 무료 티어는 이전 계정 이력으로 만료됨
- **보완 (2026-09-18)** — **Redis 는 두지 않는다.** 서버 한 대면 카운터를 공유할 상대가 없다. 호출 제한 카운터는 앱 메모리, Refresh 토큰은 MySQL 테이블. 서버 2대부터 (기획서 백로그)
- **보완 (2026-09-17, 인스턴스 생성 시)** — t3.medium(x86) → **ARM Graviton(t4g). 지금은 t4g.small(2GB), Ollama 가 들어오는 시점에 t4g.medium(4GB)**
  - 시간당(콘솔 표시가, 서울) — t3.medium $0.052 / t4g.medium $0.0416 / t4g.small $0.0208
  - 월 추정(730시간 + 디스크 30GB gp3 + 공인 IPv4, VAT 포함, 환율 1,400원 가정) — t3.medium 약 6.8만원 / t4g.medium 약 5.7만원 / **t4g.small 약 3.3만원**
  - 작게 시작하는 이유 — 지금 올라가는 건 Spring Boot(약 400MB) + MySQL(약 500MB)뿐. 4GB 가 필요한 건 Ollama·임베딩 모델부터인데 Sprint 5 까지 기간을 알 수 없어, 안 쓰는 2GB 에 매달 약 2.4만원을 미리 내지 않는다. 유형 변경은 중지 → 변경 → 시작 5분, 탄력적 IP 라 주소도 그대로 (ADR-041 을 인프라에 적용)
  - 처음엔 t4g.medium 으로 만들었다가 같은 날 small 로 내림 — 이 변경 자체가 위 "5분"의 실측 (크레딧 사양 Standard 도 유지됨)
  - ARM 을 고를 수 있었던 이유 — jar 는 아키텍처 무관, MySQL·Nginx·Ollama 모두 arm64 공식 지원. small↔medium 은 자유롭지만 **ARM↔x86 은 인스턴스를 새로 만들어야 한다**
  - 1GB(t4g.micro, 약 2.2만원)는 탈락 — 앱 + MySQL 로 꽉 차서 배포 중 메모리 부족으로 죽을 수 있다
  - 크레딧 사양은 **Standard** — T 계열 기본값 Unlimited 는 CPU 를 오래 쓰면(Ollama 추론) 추가 요금이 붙는다. Standard 는 크레딧이 떨어지면 느려질 뿐 요금은 고정
  - OS 는 Ubuntu 26.04 LTS — MySQL 8.0 이 2026-04 지원 종료라 새 운영 서버는 최신 LTS 의 패키지를 쓴다. CI 의 `mysql:8.0` 이미지는 EC2 에 설치된 버전에 맞춰 올린다 (진행상황 로드맵)

### ADR-003. 벡터를 MySQL JSON에 저장 (벡터 DB 미사용)

- **문제** — 상호명 임베딩을 어디에 저장하고 검색할 것인가
- **대안** — 전용 벡터 DB(Pinecone, pgvector 등) / MySQL JSON + 앱에서 코사인 계산
- **선택** — MySQL JSON 컬럼에 숫자 배열로 저장, 앱에서 코사인 계산
- **근거** — 유저당 수백 개 수준이라 전체를 메모리에 올려 계산해도 충분. 인프라 추가 없음
- **감수** — 데이터가 수만 건으로 커지면 검색 성능 재검토 필요

### ADR-004. AI 처리(임베딩·LLM)는 EC2에서 구동

- **문제** — 로컬 LLM(Ollama)과 임베딩 모델을 어디서 돌릴 것인가
- **선택** — 로컬 PC가 아닌 EC2. 프라이버시 목적으로 외부 LLM API 대신 로컬 모델
- **감수** — t3.medium 메모리 4GB 안에서 경량 모델만 가능

## 데이터 무결성

### ADR-005. 소프트 딜리트 + 감사 로그를 엄격한 기준으로

- **문제** — 삭제된 데이터의 복구·추적
- **선택** — 모든 주요 테이블에 `USE_YN`. 공동 지출은 `EXPENSE_LOGS`에 변경 이력 강제 기록
- **감수** — 모든 조회 `WHERE`에 `use_yn = 'Y'`를 빠뜨리면 삭제된 행이 노출됨

### ADR-006. 낙관적 락 채택 (비관적 락 아님)

- **문제** — 동시 수정 시 나중 요청이 앞의 것을 덮어쓰는 Lost Update
- **대안** — 비관적 락(`SELECT ... FOR UPDATE`) / 낙관적 락(`VERSION` 컬럼)
- **선택** — 낙관적 락. `UPDATE ... WHERE version = ?`의 affected rows가 0이면 충돌 판정 → 409
- **근거** — 개인 가계부는 본인만 수정하므로 충돌 경로가 멀티탭·PC+모바일 동시 접속 정도로 드묾. 잠그는 비용이 대부분 낭비. 공동 가계부 정산도 같은 판단
- **감수** — 충돌 발생 시 사용자가 새로고침 후 재입력해야 함
- **구현** — 수정·삭제 모두 적용. `version`은 응답 DTO에 내려주고, 수정·삭제 요청 시 쿼리파라미터(`?version=3`)로 되돌려받음. 예외 이름은 `TransactionConflictException` (`OptimisticLockException`, `ConcurrentModificationException`은 기존 클래스와 충돌)
- **범위 — 거래에만. 카테고리엔 두지 않음** (2026-09-13 추가)
  - 덮어쓰기의 피해가 다르다. 거래는 금액이라 Lost Update 가 곧 **돈 기록이 틀어지는 것**이고,
    카테고리는 이름·이모지라 덮어써도 눈에 보이고 다시 고치면 된다
  - 카테고리는 만들고 나서 거의 건드리지 않아 동시 수정 경로가 거래보다 더 멀다
  - `PERSONAL_CATEGORIES` 에 `VERSION` 컬럼이 없는 것은 이 판단의 결과 (테이블설계 참고)
- **낙관적 락이 잡지 못하는 것 — 삭제된 참조** (2026-09-13, 8단계 화면 QA 에서 실제로 밟음)
  - `version` 은 "행은 살아 있는데 값이 바뀐 경우"만 판정한다. 소프트 딜리트된 행은
    조회에서 빠져 `null` → 404 로 가므로 낙관적 락 경로를 아예 지나가지 않는다
  - 화면이 카테고리 목록을 한 번만 불러오면, 다른 탭에서 지운 카테고리가 드롭다운에 남아
    그것으로 저장 시 404. 카테고리에 `version` 을 붙여도 이 경로는 고쳐지지 않는다
  - **해법은 낙관적 락이 아니라 참조 목록을 최신으로 유지하는 것** —
    `loadTransactions()` 가 `loadCategories()` 를 함께 호출하도록 변경
  - 공동 가계부(`GROUP_CATEGORIES`)는 여러 사람이 같은 카테고리를 고치므로 상황이 다르다.
    카테고리 낙관적 락은 그때 재검토 (Sprint 4)

### ADR-007. 트랜잭션 분리 — AI 분석 중 DB 커넥션 미점유

- **문제** — OCR·LLM 호출이 몇 초 걸리는 동안 DB 커넥션을 붙잡으면 커넥션 풀 고갈
- **선택** — 임시 저장(`RECEIPT_ANALYSIS`)과 최종 저장(거래 테이블)을 별도 트랜잭션으로 분리

### ADR-008. `TRANS_TYPE` 컬럼 유지 (의도적 비정규화)

- **문제** — `PERSONAL_TRANSACTIONS.TRANS_TYPE`이 `PERSONAL_CATEGORIES.CATEGORY_TYPE`과 중복. `CATEGORY_TYPE`은 불변이라 스냅샷 명분도 없음
- **대안** — 컬럼 삭제 (모든 조회에 카테고리 조인 강제) / 유지 (동기화 책임)
- **선택** — 유지. 값은 클라이언트가 보내지 않고 **서버가 카테고리를 조회해 파생** (요청 DTO에 `transType` 없음)
- **근거** — 통계(흑자/적자 비율, 6개월 추이)는 카테고리와 무관한 타입별 집계라 조인이 순수 낭비. 서버 파생이면 값이 어긋날 경로가 거래 INSERT/UPDATE 한 곳뿐
- **감수** — 정규화 위반. 동기화 책임이 서비스 코드에 있음

### ADR-009. 좌표는 `BigDecimal`, 금액은 `Long`

- **문제** — `DECIMAL(10,7)` 좌표와 `BIGINT` 금액의 자바 타입
- **선택** — 좌표 `BigDecimal`, 금액 `Long`
- **근거** — `double`은 부동소수점이라 좌표 끝자리가 틀어져 지도 핀이 밀림. 금액은 정수라 `Long`으로 충분 (BIGINT SIGNED와 64비트 1:1)
- **주의** — JS `Number`는 약 9007조까지만 정밀. 금액 상한(1조)이 그 아래라 프론트 정밀도 문제 없음

## 인증 · 보안

### ADR-010. JWT Access 15분 / Refresh 14일 + 로테이션 + 재사용 탐지

- **문제** — 토큰 탈취 시 피해 범위
- **선택** — Access는 짧게, Refresh는 httpOnly+Secure 쿠키 + 서버 저장. 재발급 시 로테이션. 무효화된 Refresh로 재발급 시도하면 탈취로 간주해 전 세션 강제 로그아웃
- **감수** — Refresh를 서버에 저장하므로 매 재발급마다 DB 조회

### ADR-011. 소셜 로그인 동일 이메일 자동 연동 안 함

- **문제** — 이메일/비밀번호로 가입한 계정과 같은 이메일로 소셜 로그인 시도
- **대안** — 자동 연동 / 별도 안내
- **선택** — 자동 연동하지 않고 별도 안내
- **근거** — 소셜 제공자의 이메일 인증 수준을 신뢰할 수 없음. 계정 탈취 경로가 될 수 있음

### ADR-012. 에러 응답 분리 — API는 텍스트, 페이지는 HTML

- **문제** — API 호출 에러와 페이지 접근 에러가 같은 핸들러를 타면 JS `fetch`가 HTML을 받거나 브라우저가 JSON을 그대로 보여줌
- **선택** — `@RestControllerAdvice(annotations = RestController.class)`로 범위 한정. `CustomErrorController`가 `/api`로 시작하면 `ResponseEntity`, 아니면 HTML forward
- **추가** — 최종 `Exception` 핸들러는 `e.getMessage()` 노출 없이 고정 문구 (DB 스키마 노출 방지). JSON 파싱 실패·타입 불일치는 400

### ADR-013. `USER_ID`를 "공개 핸들"로 재정의

- **문제** — 소셜 전용 계정은 `USER_ID`가 NULL. 로그인 식별자로 쓸 수 없음
- **선택** — 로그인 식별자는 이메일. `USER_ID`는 유저 검색용 "공개 핸들"로 재정의하고, 유저 검색 기능 만들 때 가입 폼에 추가 (그전까지 NULL)

## AI 파이프라인

### ADR-014. Clova 일반 OCR (영수증 특화 대신)

- **문제** — 어떤 OCR을 쓸 것인가
- **대안** — Clova 영수증 특화 OCR / Clova 일반 OCR
- **선택** — 일반 OCR
- **근거** — 실제 입력은 종이 영수증보다 뱅킹앱·결제알림 캡처 비중이 높을 것으로 판단. 월 100회 무료
- **감수** — 영수증 특화가 주는 구조화된 필드(품목·합계)를 못 받음. 파싱을 직접 해야 함

### ADR-015. 정규식 우선, LLM은 실패 시에만

- **문제** — 파싱을 LLM에 전부 맡기면 비용·지연·정확도 불안정
- **선택** — 정규식으로 금액/날짜/결제대상을 먼저 시도, 실패 시에만 LLM 보조 호출. 은행앱별 패턴은 실제 부딪히며 하나씩 등록
- **감수** — 패턴 등록이 수작업. 새 은행앱 형식이 오면 처음엔 LLM 경로를 탐

### ADR-016. 임베딩 검색 → 없으면 LLM 분류

- **문제** — 매번 LLM을 부르면 느리고 정확도가 들쭉날쭉
- **선택** — 본인 과거 내역을 임베딩 유사도로 먼저 검색. 있으면 그때 카테고리·메모 추천(LLM 미호출). 없으면 LLM에 카테고리 목록을 주고 선택 또는 신규 제안
- **근거** — 같은 가게를 반복 방문하는 소비 패턴상 대부분 임베딩에서 잡힘. LLM은 신규 상호에만
- **검증 계획** — Sprint 2에서 LLM 단독 정확도를 먼저 측정하고, Sprint 3에서 임베딩 도입 후 같은 샘플 30장으로 비교

### ADR-017. AI 결과는 자동 저장하지 않음

- **문제** — AI가 뽑은 금액·카테고리를 바로 저장할 것인가
- **선택** — 유저 확인·수정 후 저장
- **근거** — 돈 관련이라 잘못 저장되면 신뢰를 잃음. 100% 자동은 위험

### ADR-018. 카테고리 이름 중복 차단 (구현 예정)

- **문제** — '식비'와 '식비 '가 둘 다 있으면 AI 분류가 흔들림
- **선택** — 이름 중복을 막기로 결정. 구현은 Sprint 2 AI 붙이기 전
- **근거** — AI 분류 정확도

## 개인 가계부

### ADR-019. 카테고리 2계층 제한

- **문제** — 카테고리 깊이
- **선택** — 대분류-소분류 2계층만
- **근거** — 더 깊으면 입력이 귀찮고 AI 분류 정확도가 떨어짐
- **구현** — `validateParent`: 부모 존재/소유/타입일치/2계층/미분류아님/자기자신아님. 수정 시 자식이 있으면 소분류로 못 내려감

### ADR-020. '미분류'는 시스템 예약어

### ADR-025. 매퍼 반환 타입 — `WHERE` 조건으로 0행이 가능하면 `int`

- **문제** — `updateCategory`는 `void`인데 `updateTransaction`은 왜 `int`인가
- **근거** — `updateCategory`는 `WHERE`가 PK 하나뿐이고 서비스가 직전에 존재를 확인하므로 항상 1행. 0행이 불가능해 반환값이 무의미. `updateTransaction`은 `version` 조건 때문에 "행은 존재하는데 조건에 안 맞는" 0행이 가능하고, 그게 곧 충돌 신호라 `int`로 받아야 함
- **정리** — INSERT는 조건절이 없어 성공=1/실패=예외라 `void`. `version` 조건을 넣은 UPDATE는 의도적으로 실패 가능한 쿼리이므로 `int`

### ADR-026. 타임존 — JVM 기본값을 Asia/Seoul로 고정

- **문제** — `@PastOrPresent`와 `LocalDate.now()`가 JVM 기본 타임존을 씀. EC2가 UTC면 한국 시간 오전 9시 이전에 등록한 오늘 거래가 "미래"로 차단됨
- **대안** — UTC 저장 + 표시 시 변환 / 코드마다 `ZoneId` 명시 / JVM 기본값 고정
- **선택** — JVM 기본값 고정
- **근거** — 국내 전용 서비스이고 `TRANS_DATE`가 시각 없는 `DATE`라 UTC 변환은 오버엔지니어링. 고정하면 `@PastOrPresent`가 별도 코드 없이 정확해짐
- **구현** — `LedgerApplication`에 `@PostConstruct` + `TimeZone.setDefault(...)`.
  `-Duser.timezone` 플래그는 IDE·gradle·test·CI·systemd 다섯 군데에 따로 걸어야 하고
  빠뜨려도 에러 없이 오전 9시 이전 거래만 조용히 400이 난다 (`-parameters` 와 같은 실패 구조, 트러블슈팅 1).
  `main()` 안에서 설정하는 방법은 테스트가 `main()`을 거치지 않아 **테스트만 다른 타임존**이 되므로 탈락.
  `spring.jackson.time-zone` 은 JSON 직렬화만 바꿔서 `LocalDate.now()`·`@PastOrPresent` 에 영향이 없음
- **주의 — JVM 과 MySQL 은 별개** — 타임존을 읽는 주체가 둘이다.
  `LocalDate.now()`·`@PastOrPresent` 는 JVM 이, `CREATED_AT DEFAULT CURRENT_TIMESTAMP` 는 MySQL 이 본다.
  어긋나면 한 테이블에 "9시간 다른 두 개의 지금"이 섞인다:
  ① `CREATED_AT` 이 밀려 `RECEIPT_ANALYSIS` 청소 스케줄러(기준이 `CREATED_AT`)가 오판
  ② 앱이 만든 `EXPIRES_AT`(`AUTH_VERIFICATIONS` 30분)을 DB `NOW()` 와 비교하면
     토큰이 즉시 만료되거나 9시간 넘게 살아있음 — 비번 재설정에서 바로 터짐
  ③ 시각 없는 `DATE`(`TRANS_DATE`)는 영향이 적고, 위험한 건 시각이 있는 컬럼
- **원칙** — 타임존은 한 값으로 정하고 **JVM · MySQL · OS 세 계층이 모두 `Asia/Seoul`**.
  로컬 맥은 OS 가 이미 KST 라 MySQL 도 따라가 문제가 보이지 않는다. EC2 에서만 드러남 (배포 시 확인)

### ADR-028. `version`은 쿼리파라미터로 전달

- **문제** — 수정·삭제 시 `version`을 어떻게 받을 것인가

### ADR-035. 예외 클래스는 도메인별로 분리

- **문제** — 거래의 404/403/409에 어떤 예외를 쓸 것인가
- **대안** — 도메인별 신규 클래스 / 공용 `NotFoundException`·`AccessDeniedException`으로 통합
- **선택** — 도메인별. `TransactionNotFoundException`, `InvalidTransactionAccessException`, `TransactionConflictException`
- **근거** — 기존 카테고리 예외가 이미 도메인별이라 섞으면 일관성이 깨짐. 공용으로 가려면 잘 돌아가는 카테고리 예외 4개를 리팩터링해야 해서 YAGNI 위반. 예외 클래스는 8줄이라 증가 비용이 거의 없고, 로그에 클래스명만 보고도 출처를 알 수 있음

### ADR-036. insert 직후 `version`은 서비스에서 0을 세팅

- **문제** — INSERT 문에 `version` 컬럼이 없어 DB의 `DEFAULT 0`이 채우는데, `useGeneratedKeys`는 PK만 자바 객체로 가져오므로 도메인 객체의 `version`이 null로 남음. 그대로 응답하면 `{"version": null}`이 나가고 프론트가 등록 직후 수정할 때 `?version=null`로 깨짐
- **대안** — 서비스에서 `setVersion(0)` / insert 후 `findByTransNum` 재조회
- **선택** — `setVersion(0)`
- **근거** — DDL의 `DEFAULT 0`은 우리가 직접 정의한 값이라 바뀔 일이 없음. 쿼리 한 번을 아끼고 코드도 단순
- **감수** — DDL의 DEFAULT가 바뀌면 이 값도 같이 고쳐야 함
- **연관** — 수정 응답도 같은 이유로 `version + 1`을 직접 담아야 함 (DB에서 올라간 값이 자바 객체에 반영되지 않음)

### ADR-037. 패키지는 계층별 유지 (도메인별 분리는 Sprint 4 전에 재검토)

- **근거** — 기능 하나당 파일이 5~6개 수준이라 구조가 복잡한 게 아니라 기능이 늘어난 것. 재배치하려면 36개 파일의 `package` 선언과 import 를 전부 손봐야 하는데, 현재 코드가 정상 동작하므로 YAGNI 위반

### ADR-038. 계산·판단은 서버, 뷰는 표시만

- **문제** — 통계 설계 중 전체 스캔. 프론트가 `'미분류'` 문자열 비교(2곳)와 `hasChildren` 계산으로 업무 규칙을 서버와 중복 구현하고 있었음. 예약어 이름을 바꾸면 한쪽만 바뀌고, 규칙이 바뀌면 두 곳을 고쳐야 함
- **선택** — 서버가 판단한 결과를 응답 DTO에 Boolean 으로 실어 보냄 (`isDefault`, `hasChildren`). 프론트는 읽어서 버튼 숨김·select 잠금만
  - `hasChildren` 목록 조회 시엔 카테고리마다 `countChildren` 을 날리지 않고(N+1) 목록 안의 `parentCategoryNum` 집합으로 계산
- **경계** — 받은 데이터만으로 답이 하나인 것(포맷, 부호, 정렬·그룹핑)은 뷰에 남김. 대분류→소분류 묶어 그리기는 표시 정렬로 봄
- **같은 커밋에서 통일한 것** — 매퍼 `@Param` 전부 명시, 컨트롤러 응답 `status().body()` 형태, 응답 DTO 애노테이션 기준(서버가 채우면 불변). `PersonalTransactionResponseDto` 는 MyBatis resultType 으로 직접 쓰여 setter 유지 - 예외로 주석 기록
- **미룬 것** — 거래 화면 합산(수입/지출/잔액)은 통계 API 가 같은 값을 내려주게 되면 그때 교체 → 2026-09-17 교체 (ADR-040)

### ADR-039. 개인 통계 — 수입 대비 지출 null, 합계는 봉투 합, month 검증은 입구에서

- **문제** — 통계 조립(`StatisticsResponseDto`)에서 세 가지를 정해야 했다. ① 수입 0인 달의 수입 대비 지출 ② 수입합·지출합을 어디서 가져올지 ③ `month=13` 이 500 나는 것
- **① 수입 대비 지출(지출 ÷ 수입 × 100)** — 수입 0 이면 `null`
  - 대안: 0 / 100 / null. 0 은 "지출이 없다" 는 거짓, 100 도 의미 없음
  - "계산 불가" 라는 판단 자체가 서버 몫(ADR-038). 프론트는 null 이면 `-` 표시
  - 용어는 **"수입 대비 지출"** (옛 이름 "소비율" 은 무엇 대비인지 안 보여서 2026-09-17 변경). 필드명 `expenseRatio`·계산은 그대로
  - 봉투 비율엔 0 나누기 방어가 없는데 여기엔 있는 이유 — 봉투는 분모 0 ⇔ 줄 없음 ⇔ 루프 안 돎 이라 나눗셈에 도달하지 않는다. 수입 대비 지출은 수입 0 이어도 지출이 있으면 나눗셈이 실행된다
- **② 합계 출처** — 봉투 목록 `amount` 합
  - 대안: 봉투 합 / 6개월 추이의 마지막 원소. 둘 다 새 쿼리는 없고 값도 같다
  - 봉투 합을 고른 이유 — 봉투 비율의 분모와 같은 숫자라 "비율 다 더하면 100" 이 합계와 맞아떨어진다. 추이 마지막 원소는 "마지막 = 보는 달" 이라는 위치 가정이 숨는다
  - QA 에서 요약·봉투·추이 셋이 같은 값인지 확인한다 (`test-statistics.sh` 1번)
- **③ month 범위** — `@RequestParam @Min(1) @Max(12)` + `HandlerMethodValidationException` 400 핸들러 (A안)
  - 대안 B: `DateTimeException` 400 핸들러 하나. 서버 내부 날짜 계산 버그까지 "사용자 잘못" 으로 덮어버려 탈락
  - 왜 DTO 필드가 아니라 파라미터에 거나 — 일관성 기준은 "필드" 가 아니라 **"값이 들어오는 입구"**. body 는 DTO 필드에, 쿼리스트링은 `@RequestParam` 에. 둘 다 컨트롤러 입구에서 바인딩 직후 검증되는 같은 층. int 둘 받자고 요청 DTO 를 두는 건 YAGNI, 파라미터가 늘면 그때 DTO 로 옮기면 애노테이션도 따라간다
  - 주의: 컨트롤러 클래스에 `@Validated` 를 붙이면 AOP 가 가로채 `ConstraintViolationException` 이 되어 핸들러가 안 잡힌다. Spring 6.1+ 내장 메서드 검증에 맡긴다
  - `/api/transactions` 의 month 도 같은 구조라 함께 적용
- **감수** — 수입 대비 지출 null 을 프론트가 매번 처리해야 함. 합계를 봉투에서 더하므로 봉투 로직이 바뀌면 합계도 따라 바뀜(의도된 결합)

### ADR-040. 서버/뷰 경계는 유연하게 — 거래 화면 합계는 통계 API, 회색은 뷰에 둔다

- **문제** — ① 거래 화면 합산을 서버 값으로 바꾸면 요청이 하나 는다(카테고리·목록 + 통계). 허용할 것인가
  ② "뷰는 표시만"(ADR-038)을 어디까지 밀 것인가. 전체 스캔(JS 628줄)에서 위반 1건(거래 화면 합산) 외에 회색이 나왔다 —
  통계 봉투 펼침 판정, "N건", 상위 select 후보 거르기, HTML 입력 제약. 전부 서버로 옮기면 API 가 화면 모양에 묶인다
- **대안 (①)** — A. `/api/statistics` 별도 호출 / B. 거래 목록 응답에 합계를 같이 실음 / C. 프론트 합산 유지
- **선택 (①)** — A + 세 요청을 `Promise.all` 로 동시에
  - B 는 요청 하나를 아끼는 대신 합계 계산이 거래·통계 두 서비스에 생겨 ADR-039 ②(합계 출처 하나)를 뒤집는다. 응답 모양이 배열 → 객체로 바뀌어 `test-transaction.sh` 52케이스도 손봐야 한다
  - C 는 페이징을 붙이는 순간 "보이는 20건의 합"이 되어 통계 화면과 어긋난다
  - 직렬 2회(카테고리 → 목록)였던 것이 동시 3회가 되어 기다리는 횟수는 오히려 2 → 1
- **선택 (②)** — 나누는 것 자체가 목적이 아니다. 목적은 **"규칙·돈 계산을 바꿀 때 한 곳만 고치면 되는가"**. 질문 두 개로 정한다
  - 틀리면 돈·규칙이 틀어지는가, 다른 화면도 같은 값을 보여줘야 하는가 → 서버
  - 이 화면에서만 의미 있는 모양인가 → 뷰
- **회색 판정 기록**
  - 통계 봉투 펼침(`children` 에 자기 아닌 줄이 있는가) — 뷰 유지. 이 화면의 접힘 모양이고, Boolean 을 내려주면 DTO 가 화면에 묶인다
  - "N건"(`transactions.length`) — 뷰 유지. 보이는 줄 수라 지금은 참. 페이징 때 서버 totalCount 로
  - 상위 카테고리 select 후보 거르기, HTML `min/max/maxlength`, `transDate.max` — 입력 보조. 최종 판정은 서버(`validateParent`, `@Valid`)
- **감수** — 거래 화면이 쓰지 않는 봉투·추이까지 받는다(집계 SQL 2회). 느려지면 합계 전용 엔드포인트를 그때 분리.
  통계 요청만 실패하면 화면이 갱신되지 않는다 — 조회 실패 처리(뷰 대공사)와 같이

### ADR-041. 설계 기준은 "바꿀 때 싸게 바뀌는가" — 리팩토링은 다음 변경 직전에

- **검사 방법** — 곧 올 변경을 정해 "몇 군데를 고치나"를 센다 (설계-체크리스트 11번)

    - 월 이동 JS 2벌 → 달력 뷰(세 번째 복제) 직전에 util 로

### ADR-042. 1차 배포 — 프로파일은 "다른 값만", QA 스크립트를 배포 전 게이트로

- **문제** — ① `application.yml` 하나가 그대로 운영에 가면 매퍼 `DEBUG` 로그가 켜진 채 돈다 (사용자 금액·메모가 SQL 바인딩 값으로 로그에 평문 기록 + 디스크 증가)
  ② CD 를 붙이면 "push = 운영 반영"인데 CI 는 `@Test` 1개뿐. 회귀 146케이스(`qa/test-*.sh`)는 사람이 기억해서 돌려야 한다
- **선택 (①)** — Spring 프로파일. 공통 `application.yml` + `application-local.yml`(DEBUG 3줄만). EC2 는 systemd 환경변수 `SPRING_PROFILES_ACTIVE=prod`
  - **기본값은 운영에 안전한 쪽** — DEBUG 를 공통에 두고 prod 에서 끄는 대안은 프로파일 지정을 빠뜨리면 조용히 DEBUG 로 운영된다 (`-parameters`·타임존 플래그와 같은 실패 구조, ADR-026).
    local 에서만 켜면 빠뜨렸을 때 "SQL 로그가 안 보임"으로 드러난다
  - 프로파일 파일엔 공통과 **다른 값만** — 전체 복사는 설정 하나 바꿀 때 두 곳을 고치게 된다 (ADR-041)
  - `application-prod.yml` 은 만들지 않음 — 지금 넣을 값이 없다. 운영 전용 값이 처음 생길 때(Refresh 쿠키 `Secure` 등)
  - 파일은 커밋한다 — gitignore 기준은 "비밀인가". 로그 레벨은 비밀이 아니고, 비밀값은 전부 `${ENV}`
- **하지 않은 것 — DB URL 환경변수화(`${DB_URL:...}`)**
  - 환경변수로 빼는 기준은 "환경마다 값이 다른가 + 비밀인가". DB 주소는 맥북·CI·EC2 모두 자기 자신의 MySQL(`localhost`)이라 같고(ADR-002), 비밀도 아니다
  - DB 를 인스턴스 밖으로 옮기게 되면 그때 이 한 줄만 바꾸면 된다 — 미뤄도 비용이 같다 (YAGNI)
  - JDBC `serverTimezone` 옵션도 붙이지 않는다 — 계층이 어긋났을 때 드라이버가 덮는 옵션이고, `DEFAULT CURRENT_TIMESTAMP` 는 MySQL 이 혼자 계산해 이걸로 고쳐지지 않는다. OS·MySQL 을 KST 로 맞추는 게 해법 (ADR-026)
- **선택 (②)** — 게이트 도입. `build → qa → deploy`, deploy 는 `needs: qa`. QA 는 Actions 러너 안(일회용 MySQL 컨테이너)에서 돌고 운영 DB 를 건드리지 않는다
  - 대안: 게이트 없이 CD 만 / JUnit 전환(Sprint 4)까지 대기. 전자는 "배포 전 QA"를 사람이 기억해야 하고, 후자는 그때까지 운영이 무방비
  - 스크립트가 대화형(`read`, `mysql -p`)이고 `summary()` 가 실패해도 종료코드 0 이라 그대로는 못 넣는다 → 환경변수 기반 비대화 모드 + `exit 1`. 로컬 기본 동작은 유지
  - **시점은 CD 가 게이트 없이 1회 성공한 직후** — 같이 만들면 실패 원인(SSH·systemd vs 테스트)이 구분되지 않는다
- **감수** — 배포 1회가 몇 분 느려진다. curl 스크립트는 JUnit 보다 느리고 실패 원인 표시가 거칠다 (Sprint 4 에서 JUnit 으로 교체하면 qa 잡의 내용만 바뀌고 파이프라인 모양은 그대로)
- **결과 (2026-09-20, 4단계)** — 게이트 가동. 실측으로 배포 1회 약 2분 → 약 3분
  - 검증은 양쪽 다 — 정상일 때 통과(CI #53) + **일부러 `@Min` 한 줄을 깨서 build ✅ / qa ❌ / deploy skipped**(CI #54) → revert 후 복귀(#55). 빌드가 못 보는 걸 게이트가 본다는 증명
  - 구현하며 더한 결정 — 검사한 jar 를 그대로 배포(artifact 재사용) / CI MySQL 을 운영과 같은 8.4 로 / **러너·DB 컨테이너에 `TZ=Asia/Seoul`**(ADR-026 의 3계층을 CI 에도 — 안 하면 KST 00~09시에만 "미래 날짜" 케이스가 깨진다) / 계정 시드는 `reset-all.sh` 재사용(계정 목록 한 곳)

### ADR-043. EC2 MySQL — root 는 `auth_socket` 유지, 앱 계정 하나에 그 DB 권한만

- **문제** — 운영 MySQL 의 관리자 계정과 앱 계정을 어떻게 둘 것인가
- **① root 비밀번호를 만들 것인가 — 만들지 않는다 (`auth_socket` 유지)**
  - 실측 — 설치 직후 `root@localhost` 의 플러그인이 `auth_socket`. 3306 은 `127.0.0.1` 에만 바인딩(보안 그룹과 별개로 MySQL 자체가 밖을 안 받는다)
  - `auth_socket` 은 "비번이 없는 상태" 가 아니라 **비번을 아예 받지 않는 상태**다. 유닉스 소켓의 OS 사용자 이름으로만 인증하므로 TCP 로는 원천적으로 불가능하고, 빈 비번으로도 어떤 비번으로도 들어올 수 없다. `sudo mysql` 이 통하는 건 sudo 가 OS root 를 주기 때문
  - 즉 MySQL root 로 들어오려면 먼저 **OS root 를 가져야 한다.** 그런데 sudo 를 쥔 공격자에게 MySQL 비번은 장애물이 아니다 (`--skip-grant-tables` 재시작, `EnvironmentFile` 직접 읽기)
  - 비번을 만들면 바뀌는 건 **지금 존재하지 않는 비밀이 하나 생기는 것**뿐이다. 관리할 값이 늘고 유출 경로가 생기는데 막아지는 경로는 없다 (CLAUDE.md "비밀값 · 개인정보")
  - `mysql_secure_installation` 은 그래도 돌린다 — 익명 사용자·원격 root·`test` DB 제거. 다만 우분투 패키지는 앞의 둘이 처음부터 없어서(실측) **확인 작업에 가깝다.** 실행이 공짜인데 하나라도 남아 있으면 제일 아픈 종류라서 돌린다
  - VALIDATE PASSWORD 컴포넌트는 설치하지 않음 — 계정을 만드는 사람이 한 명이고 비번은 `openssl rand` 랜덤 값이라, 막아 줄 실수가 없고 `ALTER USER` 때 방해만 된다
- **② 앱 계정을 몇 개 둘 것인가 — 하나 (A안)**
  - 대안 A: 앱 계정 하나에 `GRANT ALL PRIVILEGES ON ledger_db.*` (Flyway 도 이 계정) / B: 마이그레이션용(DDL)과 실행용(DML) 분리
  - 권한 하한 — V1 은 테이블 18개·FK 34개를 만들고 Flyway 가 자기 이력 테이블도 쓴다. `SELECT/INSERT/UPDATE/DELETE` 만 주면 **첫 기동에서 V1 이 실패한다**
  - A 를 고른 이유 — B 가 막는 건 "공격자가 테이블을 DROP 하는 것" 인데, 거기까지 간 공격자는 이미 DML 로 모든 거래를 읽고 고칠 수 있다. 돈 기록에서 더 아픈 쪽은 삭제가 아니라 열람·변조이고 삭제는 백업(5단계)으로 돌아온다. B 는 환경변수가 2개 늘어(`spring.flyway.username/password`) 맥·CI·EC2 세 군데를 다 고쳐야 한다 — 방금 세운 "환경변수는 3개가 전부" 표가 깨진다
  - 계정 이름은 맥·CI 와 같은 `ledger_app` — 이름이 환경마다 다르면 기억할 게 는다. **값(비번)만 환경별로 다르게**
- **감수** — 앱이 뚫리면 `ledger_db` 안에서는 무엇이든 할 수 있다. 공동 가계부(Sprint 4) 직전에 실행 계정 DML 분리를 재검토한다 (남의 돈 기록이 들어오는 시점)

### ADR-044. DB collation 은 기본값으로 세 환경 통일 — 뒤 공백 판단은 서버가

- **문제** — EC2 `ledger_db` 를 만들면서 collation 을 정해야 했다. 확인해 보니 **세 환경이 이미 어긋나 있었다**
  - 실측(2026-09-17) — 맥 `ledger_db` 는 `utf8mb4_unicode_ci`(누군가 만들 때 명시적으로 준 값. 같은 서버 기본값은 `0900_ai_ci`) / CI 컨테이너는 `MYSQL_DATABASE` 가 서버 기본값으로 만들어 `utf8mb4_0900_ai_ci` / EC2 는 그냥 만들면 `0900_ai_ci`
  - 저장소 전체에 `COLLATE` 를 명시한 곳이 **한 군데도 없다.** V1 은 테이블마다 `DEFAULT CHARSET=utf8mb4` 만 쓰므로 collation 은 DB 기본값이 컬럼까지 그대로 내려간다
  - **차이의 실체는 뒤 공백 하나** — `unicode_ci` 는 PAD SPACE 라 `'식비' = '식비 '` 가 참, `0900_ai_ci` 는 NO PAD 라 거짓. 둘 다 `ci` 라 대소문자는 똑같이 구분하지 않는다. 한글 데이터에서 체감되는 차이는 사실상 이것뿐
- **선택 (collation)** — **아무 데도 명시하지 않고 기본값 `utf8mb4_0900_ai_ci` 로 통일.** 로컬 `ledger_db` 를 지우고 다시 만들어 맞췄다
  - 대안: `unicode_ci` 로 통일. 그러면 EC2·CI 양쪽에 명시를 넣어야 하고 **앞으로 만드는 모든 환경에서 기억해야 한다** (ETC 위반)
  - 기본값을 따르면 새 환경이 자동으로 맞는다 — 프로파일 때 세운 "기본값이 운영에 안전한 쪽" 과 같은 구조 (ADR-042)
  - **지금이 가장 싼 시점** — 운영에 데이터가 없다. 나중에 바꾸려면 `ALTER TABLE ... CONVERT` 를 실데이터 위에서 돌려야 한다
  - 검증 — 빈 DB 에 Flyway V1 재실행(`Empty Schema` → `Successfully applied 1 migration`) 후 146케이스 전부 통과. 이 과정 자체가 **EC2 첫 기동의 리허설**이다
- **선택 (뒤 공백 판단)** — **DB collation 에 맡기지 않고 서버가 입구에서 정규화한다.** `CategoryRequestDto` 에 `setCategoryName()` 을 직접 써서 `strip()`
  - 실제 웹 서비스의 순서 — ① 입구에서 정규화 ② 정규화된 값으로 검증 ③ 정규화된 값을 저장 ④ DB 유니크 제약을 마지막 방어선으로. Django 는 폼 문자열을 기본 trim 하고 Rails 엔 `normalizes` 가 있다. Spring 은 안 해 주므로 직접 넣는다
  - 실측으로 **③ 이 빠져 있었다** — 서비스 32·95 행이 `'미분류'` 와 비교할 때만 `trim()` 하고, 저장은 원본을 그대로 넣고 있었다. `@NotBlank` 는 빈 값만 막고 뒤 공백은 막지 않는다
  - 세터를 DTO 에 둔 이유 — create/update 가 같은 DTO 를 쓰므로 **한 곳만 고치면 두 경로가 다 막힌다.** Jackson 이 이 세터로 값을 넣고 그 뒤에 `@Valid` 가 돌아서, 검증·예약어 검사·저장이 전부 정리된 값만 본다. Lombok 은 직접 쓴 세터가 있으면 그 필드 세터를 만들지 않는다
  - `trim()` 이 아니라 `strip()` — 한글 입력기의 전각 공백(U+3000)까지 지운다
  - 규칙을 collation 에 숨기지 않는 이유 — 판단은 서버가 한다(ADR-038). DB 설정에 숨기면 DB 를 옮기거나 컨테이너 버전을 바꿀 때 조용히 동작이 달라진다
  - 서비스의 `.trim()` 2곳은 제거 — 정규화가 DTO 한 곳에만 있게 (ADR-041)
- **감수**
  - 동작이 하나 바뀐다 — `"식비" + 공백 30개` 는 예전엔 `@Size(max=20)` 으로 400 이었는데 이제 공백을 지운 뒤 길이를 세므로 201. 의도한 변화
  - 로컬 개발 데이터가 한 번 날아갔다 (`reset-all.sh` 로 복구)
  - 이름 **중복 차단**(ADR-018)은 여전히 미구현. 이번에 한 건 정규화까지다

### ADR-045. 테이블명은 소문자로 통일 — 대소문자 판단을 OS 설정에 맡기지 않는다

- **문제** — EC2 첫 기동(2-5)에서 Flyway 는 19테이블을 만들었는데 가입 API 가 500. 로그 마지막은 `Table 'ledger_db.users' doesn't exist`.
  V1 은 `CREATE TABLE USERS`(대문자), 매퍼 XML·qa SQL 은 `FROM users`(소문자)였다
- **원인** — `lower_case_table_names` 가 OS 마다 다르다. 맥은 파일시스템이 대소문자를 구분하지 않아 `2`(저장은 준 대로, **비교는 무시**), 리눅스는 `0`(그대로 저장, **그대로 비교**).
  같은 SQL 이 맥에선 되고 EC2 에선 안 된다. 실측 — 저장소에서 대문자는 V1 한 파일뿐(CREATE 18 + REFERENCES 34 = 52곳), 소문자는 매퍼 22곳 + qa SQL 18곳
- **대안**
  - A: 매퍼·qa 를 대문자로 — 파일 7개를 고치고, 앞으로 쿼리를 쓸 때마다 대문자를 기억해야 한다
  - B: **V1 을 소문자로** — 파일 1개. 저장소 다수가 이미 소문자이고, MySQL 공식 권고도 "전부 소문자로 통일"
  - C: EC2 MySQL 을 `lower_case_table_names=1` 로 — **탈락.** MySQL 8.0+ 는 데이터 디렉토리 초기화 시점에만 정할 수 있어 나중에 바꾸면 서버가 기동을 거부한다.
    CI 컨테이너에도 같은 설정을 걸어야 하고, 무엇보다 저장소의 불일치를 **서버 설정으로 덮는 것**이라 새 환경마다 기억해야 한다 (ETC 위반, ADR-044 의 collation 판단과 같은 구조)
- **선택** — B. 컬럼·제약·인덱스 이름은 그대로 뒀다 — 테이블명이 아니고, 컬럼명은 MySQL 이 어느 OS 에서든 대소문자를 구분하지 않는다. 예약어 `groups` 는 백틱 유지
- **시점** — **운영 DB 가 비어 있는 지금이 가장 쌌다.** V1 이 바뀌면 Flyway 체크섬이 어긋나 맥·EC2 의 DB 를 지우고 재적용해야 하는데, 지금은 둘 다 데이터가 없다.
  데이터가 쌓인 뒤라면 `RENAME TABLE` 마이그레이션(V2)을 써야 하는데, 그건 맥(`lctn=2`)에서 "이미 있는 테이블"로 실패할 수 있어 환경마다 다르게 동작한다 (ADR-044 와 같은 "지금이 제일 싼 시점" 판단)
- **왜 여태 안 드러났나** — CI 는 리눅스지만 `@Test` 가 `contextLoads` 하나뿐이라 쿼리를 한 번도 날리지 않는다. 146케이스는 맥에서만 돌았다.
  **4단계 게이트(러너에서 146케이스)가 있었으면 배포 전에 잡혔다** — ADR-042 ②의 근거 보강
- **감수** — V1 을 최초 적용 이후에 수정했다 (CLAUDE.md "V1 적용 이후엔 V2 추가" 의 예외).
  그 규칙의 이유는 "이미 적용된 곳과 어긋난다" 인데 적용된 두 곳 모두 데이터가 없어 다시 만들면 그만이었다. **데이터가 생긴 뒤엔 이 예외를 쓰지 않는다**

### ADR-046. 서버의 자리 — 실행 파일은 `/opt`, 설정은 `/etc`, 비밀값 파일은 root 소유

- **문제** — jar 와 비밀값(DB 비번·JWT 시크릿)을 서버 어디에, 누구 소유로 둘 것인가
- **선택** — jar 는 `/opt/ledger/ledger.jar`(올리는 쪽 소유 755/644), 비밀값은 `/etc/ledger/ledger.env`(`root:root 600`), 앱은 `ledger` 계정으로 실행
- **근거**
  - **수명이 다르다** — jar 는 배포마다 교체, 비밀값은 서버가 사는 동안 그대로. 같은 폴더면 CD 가 디렉토리를 정리하다 비밀값을 같이 지운다
  - systemd(root)가 `EnvironmentFile` 을 읽어 환경변수로 넘긴 **뒤에** `User=ledger` 로 내려간다 → 앱 계정은 그 파일을 읽을 필요가 없다. 배포 계정(`deploy`)도 못 읽는다(3-3 실측)
  - **앱은 자기 실행 파일을 고칠 수 없어야 한다** — 뚫린 앱이 jar 를 바꿔치기하는 경로 차단
  - jar 이름은 버전 없이 고정 — 버전이 파일명에 박히면 올릴 때마다 유닛 파일을 고친다 (ADR-041)
- **감수** — 비밀값이 평문 파일이다. 서버가 늘면 Parameter Store·Secrets Manager 로 (한 대짜리엔 과함)

### ADR-047. CD 접속 경로 — 배포할 때만 22번을 러너에게 열고, 권한은 OIDC

- **문제** — 보안 그룹 22번이 "내 IP 만" 이라 GitHub Actions 러너(매번 다른 IP 의 일회용 머신)가 SSH 를 못 붙는다
- **대안** — A: 22번 전체 개방(무차별 대입 시도가 상시 들어온다) / **B: 배포할 때만 러너 IP 를 열고 닫기** / C: SSM Session Manager(22번을 아예 안 연다) / D: VPC 안 self-hosted 러너
- **선택** — B. AWS 권한은 **OIDC 역할**(장기 액세스 키 없음, 1시간 임시 자격), SSH 는 배포 전용 키 + `deploy` 계정(sudo 는 `restart` 한 줄)
  - 문이 둘이고 서로 독립 — AWS API(보안그룹 규칙) / SSH(jar 교체·재시작). 한쪽이 털려도 다른 쪽은 안 열린다
  - 정책은 액션 2개 · 보안그룹 1개 ARN. 신뢰 정책 `sub` 는 main 한정(이름 형태 + 숫자 ID 형태, 트러블슈팅 13). 와일드카드 없음
  - 닫기는 `if: always()`, 여는 단계는 같은 규칙을 먼저 지우는 자기 정리, `concurrency` 로 배포 겹침 방지
  - 서버 지문 고정(`EC2_HOST_KEY` + `StrictHostKeyChecking=yes`), 액션 전부 SHA 고정 + Dependabot, 덮어쓰기 전 `.prev` 백업
- **왜 C 가 아닌가** — 실무 정답은 "열 필요가 없게"(SSM·pull 방식)다. 다만 인스턴스 역할·에이전트 구성이 더 들고, 지금은 CD 를 처음 굴려 보는 단계. 서버·배포 경로가 늘면 C 로 (로드맵 8번)
- **감수**
  - IAM 조건 키에 포트가 없어 **"22번만" 으로는 못 좁힌다** — 이 역할은 그 보안그룹 하나에 한해 어떤 포트든 열 수 있다
  - 러너 IP 조회가 외부 서비스에 의존(`checkip.amazonaws.com`, 예비 `api.ipify.org`)
  - 러너가 강제 종료되면 규칙이 남을 수 있다(특정 IP 하나에 22번 — 다음 배포의 자기 정리가 청소)
  - 배포마다 약 10초 중단, 테스트는 `contextLoads` 하나 — 각각 로드맵 7번 · 4단계 게이트

### ADR-048. 값 3단 분류 — 비밀 / 식별자 / 공개 설정

- **문제** — CD 를 만들며 "이 값은 Secrets 인가, yml 에 적어도 되는가" 를 매번 다시 판단하고 있었다
- **선택** — ① 비밀(키·비번·토큰) → Secrets·서버 env 파일 ② **식별자(IP·계정 ID·`sg-`·ARN·서버 지문) → 이 저장소에선 Secrets** ③ 공개돼도 되는 설정(리전·계정 이름·포트) → 코드에 그대로
- **근거**
  - 실무 기본형은 비밀 = Secrets / 비밀 아닌 설정 = Variables / 상수 = 코드. 그런데 **공개 저장소는 Actions 로그도 공개**이고 Variables 는 로그에 그대로 찍힌다 → 식별자를 Secrets 로 올려 `***` 마스킹을 받는다
  - ③을 Variables 로 빼지 않는 건 환경이 하나뿐이라서 (YAGNI, ADR-042 의 "환경마다 다른가 + 비밀인가"). staging 이 생기면 그때
  - 비밀·식별자 목록표(이름·위치·무엇을 여나·유출 시 교체)는 aws-인프라.md — 사고 뒤엔 찾아볼 여유가 없다
- **감수** — 식별자까지 가려져 로그로 디버깅하기 불편하다. 필요할 땐 길이·접두만 찍는다 (트러블슈팅 13·14)
