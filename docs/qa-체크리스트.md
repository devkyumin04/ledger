# QA 체크리스트

기능 하나를 만들 때마다 아래 틀에 대입해 케이스를 뽑는다.
**케이스를 외우는 게 아니라 틀을 갖는 것**이 목적.

---

## 큰 분류 3개

| 분류 | 관점 |
|---|---|
| **정상** | 의도대로 썼을 때 제대로 되는가 |
| **실수** | 사용자가 잘못 입력했을 때 친절하게 막는가 |
| **악의적** | 남의 데이터를 건드리거나 규칙을 우회할 수 있는가 |

---

## 케이스를 뽑는 5가지 축

각 API마다 이 5개를 대입하면 대부분 나온다.

### ① 경계값
- 숫자: `0`, `1`, 최대값, 최대값+1, 음수
- 날짜: 오늘, 내일, 월초 1일, 월말, **12월** (연도 자리올림)
- 문자열: 빈 값, 최대 길이, 최대 길이+1
- 목록: 0건, 1건, 많은 건수

### ② 순서 의존
- 삭제한 것을 다시 수정하면?
- 삭제한 것을 다시 삭제하면?
- 수정하고 그 응답으로 또 수정하면? (연속 수정)
- 등록 직후 바로 수정하면?

### ③ 동시성
- 두 곳에서 동시에 수정하면? (낙관적 락 → 409)
- 오래된 version 으로 요청하면?
- 같은 요청을 두 번 보내면? (멱등성)

### ④ 권한
- 토큰 없이 호출하면? (401)
- 남의 자원을 조회 / 수정 / 삭제하면? (403)
- 남의 자원을 참조해서 내 자원을 만들면? (403)
- 수정으로 **남의 자원에 연결**하려 하면? (403 — 등록만 막고 수정을 놓치기 쉬움)

### ⑤ 누락 · 형식
- 필수 필드를 빼면? (400)
- 쿼리파라미터를 빼면? (400)
- 타입이 안 맞으면? (`"abc"` 를 숫자 자리에)
- 형식이 깨진 JSON 이면?
- 서버가 정하는 값(userNum, type 등)을 body 에 끼워넣으면? → **무시되어야 함** (Mass Assignment 방어)

---

## 응답 body 도 검사할 것

상태코드만 보면 놓치는 것들:

- 서버가 **파생**시키는 값이 제대로 들어갔는가 (예: `transType`)
- 낙관적 락의 `version` 이 **올라가서** 내려오는가
- 조인해서 가져온 값이 포함되었는가 (예: `categoryName`, `categoryEmoji`)
- 클라이언트가 보낸 위조 값이 **무시**되었는가

## 스크립트로 남길 것

일회성으로 확인하고 버리면 나중에 같은 버그가 다시 생겨도 모른다.
`qa/*.sh` 로 남겨두고 코드를 고칠 때마다 다시 돌린다.

| 스크립트 | 용도 |
|---|---|
| `qa/category-parent.sh` | 카테고리 계층 검증 (12케이스) |
| `qa/transaction-crud.sh` | 거래 CRUD (52케이스) |
| `qa/category-transfer.sh` | 카테고리 삭제 시 거래 미분류 이관 (35체크, 부수효과 검사) |
| `qa/reset-data.sql` | QA 데이터 정리 — USERS 와 '미분류' 는 유지 |
| `qa/reset-all.sql` | 전체 초기화 — 유저 포함 모두 삭제 |
| `qa/reset-all.sh` | 전체 초기화 + 테스트 계정 2개 재가입 (서버 기동 필요) |

### 실행

비밀번호는 스크립트에 하드코딩하지 않고 환경변수로 주입한다.
(`application.yml` 이 `DB_USERNAME` / `DB_PASSWORD` 를 받는 것과 같은 방식)

```
export QA_PASSWORD='<테스트 계정 비밀번호>'
sh qa/transaction-crud.sh
sh qa/category-transfer.sh
```

### 데이터 초기화 후 주의

`reset-all.sql` 로 유저까지 지웠다면 **반드시 회원가입 API 로** 계정을 다시 만든다.
SQL 로 `users` 에 직접 INSERT 하면 가입 시 자동 생성되는 '미분류'(E/I) 가 없어서
카테고리 삭제 이관이 동작하지 않는다.

## 이 방식의 한계

curl 스크립트는 **API 계층 테스트**다. 실제 HTTP 전 구간(직렬화·인증 필터·상태코드)을
검증하는 장점이 있지만:

- 서버를 띄워야 해서 CI 에서 자동 실행이 어렵다
- DB 에 데이터가 계속 쌓인다
- 실패했을 때 컨트롤러/서비스/매퍼 중 어디가 문제인지 좁히기 어렵다

그래서 실무는 **단위 테스트(JUnit) > 통합 테스트(MockMvc) > API 테스트** 순으로 비중을 둔다.
날짜 계산이나 충돌 판정 같은 순수 로직은 JUnit 이 훨씬 빠르고 CI 에서 자동으로 돈다.

→ Sprint 4 의 "깊게 팔 영역"이 JUnit 이므로 그때 단위 테스트로 전환·보강한다.
